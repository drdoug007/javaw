# Pinned dependency audit

Run `python3 runtime-target/audit.py --check-baseline` from the repository root. The command verifies all artifact identities, compiles the auditor, and scans the entire locked library closure. It defaults to offline Maven; `--online` permits missing dependency downloads. The machine-independent aggregate snapshot is `runtime-target/audit-baseline.json`. After reviewing a changed target/compiler inventory, `--update-baseline` records the new snapshot. Full reports are generated under `runtime-target/target/audit/` and are not committed.

The initial scan selected Java 17 multi-release entries from 63 JARs and found 26,625 unique classes, no duplicate class definitions, 734 resources and 28 service providers. The initial opcode/feature inventory includes 17,383 invokedynamic sites, 23,483 ATHROW instructions, 22,506 exception-table entries, 5,581 class initializers, 464 synchronized methods and 90 native declarations. Counts cover all selected library classes, including optional paths; they do not establish which facilities the first application workload must execute.

| Report | Meaning |
| --- | --- |
| `summary.tsv` / `summary.json` | Compiler revision, target Java level, roots, counts and analysis limits; JSON adds aggregated opcode/feature/bootstrap counts |
| `artifacts.tsv`, `classes.tsv` | Entire locked closure and static class-reference estimate |
| `normalized-opcodes.tsv` | Raw legacy subroutine occurrences handled by preprocessing; the audit verifies their classes can be normalized |
| `unsupported-opcodes.tsv` | All currently unadmitted instruction occurrences, grouped by artifact/opcode with first method evidence |
| `member-references.tsv` | Field/method/handle references with descriptors, counts and first referencing method; negative opcode values identify bootstrap method-handle tags |
| `bootstrap-sites.tsv` | Deterministic per-site owner/method, executable instruction ordinal, invoked descriptor, bootstrap/typed arguments, implementation-handle tag and alternate-lambda flags; control characters are escaped |
| `dynamic-runtime.tsv` | Pattern-based mechanism inventory for MethodType/MethodHandle/VarHandle operations, lookup factories, proxy factories and class/CGLIB/Byte Buddy generation boundaries; includes descriptors, counts and first sites |
| `requirements.tsv` | Initialization, handlers, strings, bootstrap sites, native/synchronized/volatile declarations and platform/reflection/I/O/concurrency lookups |
| `external-types.tsv` | Referenced types outside the locked JARs; includes JDK classes and optional integrations, not just missing dependencies |
| `resources.tsv`, `services.tsv` | Selected bundled resources and declared service providers |
| `duplicate-classes.tsv` | Conflicting class definitions; duplicates make a single-origin reachability estimate ambiguous |

The roots are `org/h2/Driver`, `org/hibernate/cfg/Configuration`, and `org/springframework/boot/SpringApplication`. A class-reference closure starts at those types and follows superclass/interface, descriptor, signature, annotation/record/nest metadata, instruction, handle and bootstrap references across all methods of each class. It initially includes 11,441 bundled classes. This is an estimate, not method-level or sound dynamic reachability: reflection strings, resources, framework conditionals, service activation, generated classes and runtime traces require separate analysis. Unreached classes are not proven removable. The JDK implementation itself is not part of the 63-JAR scan. Opcode admission alone does not establish supported semantics or member linkage.

Concrete blocker ordering from this scan:

1. Continue declaration/reference/uninitialized-object verification. Byte Buddy 1.14.11 contains legacy JSR/RET subroutines (162/77 occurrences), including `TypeCache$WithInlineExpunction.find`; normalization before ordinary frame analysis is now implemented and verified across all 61 affected methods. Other Byte Buddy requirements remain open.
2. Arrays, catchable exceptions and automatic initialization are immediate H2 requirements. H2 alone has 3,106 exception-table entries and 305 static initializers, in addition to JDBC/JDK linkage.
3. Build runtime strings/classes and required JDK members before bootstrap/reflection integration. The scan found StringConcatFactory (8,917 sites), LambdaMetafactory.metafactory (8,269), altMetafactory (46), and record ObjectMethods.bootstrap (151). Constant-dynamic scanning is tested, but the pinned selected closure initially contains no constant-dynamic sites.
4. Reflection, annotation/service/resource lookup, method handles, Byte Buddy/proxy/enhancement behavior and framework conditionals require actual startup traces and targeted tests. No report treats static analysis as a substitute for those execution gates.
5. Concurrency, memory roots and platform adapters must be implemented before claiming actual full-stack startup. H2 alone uses synchronized methods, volatile fields, concurrency APIs and I/O/NIO; background pools are not solved by the source-subset transaction implementation.
6. Optional Tomcat native/APR/OpenSSL paths account for most native declarations in this closure. They must be excluded explicitly for the initial non-web target or implemented for a selected later host mode. JDK-internal references include Spring Objenesis/Unsafe allocation and H2 extended socket options. Presence in a JAR does not make every such path mandatory for embedded JDBC.

The next runtime features must use actual-library JVM and Wasm regressions. `mvn -o -pl runtime-target test` currently passes on the JVM; it is not a Wasm integration gate yet. Synthetic auditor tests verify multi-release selection, unused-class inventory, metadata/bootstrap references, service parsing, duplicates, missing roots and deterministic output. Compiler bytecode tests continue to run independently.


The `dynamic-linkage-v40` bootstrap-site audit finds 17,383 sites: 8,269 metafactory, 46 alternate metafactory (34 serializable+bridge flags=5 and 12 serializable flags=1), 8,917 concat and 151 record bootstraps. Lambda handles include 3,680 static, 2,894 virtual, 804 special, 770 interface and 167 constructor references. Concat sites have no static constants beyond the recipe; no constant-dynamic sites occur. These actual protocols drove the bounded adapter implementation. JVM/Wasm regressions additionally execute unchanged Spring Boot 3.2.4 `PlaceholdersResolver` and `RabbitConnectionDetails$Address` bytecode, validating artifact hashes and JAR-order/module-instance independence. This establishes those isolated library paths, not Spring Boot startup or full closure compatibility.


The next dynamic-runtime milestone starts with the concrete byte-array-view calls in H2 Bits and Jackson doubleparser helpers. The `byte-array-views-v41` regression executes unchanged H2 2.2.224 Java-17-selected Bits bytecode and compares reads/writes, raw floating bits, UUID byte conversion, comparisons and failures with the JVM. Jackson's matching factory/get/set/exact-mode protocols informed the implementation; execution of its full parser is not claimed.

`dynamic-runtime.tsv` separates calls to MethodType, MethodHandle, VarHandle, MethodHandles/Lookup, Proxy, class-definition APIs, CGLIB generation factories and Byte Buddy DynamicType builders/loaders/injectors. It scans all selected classes, including optional/unreachable paths; classification is by symbolic owner/name, not dynamic dispatch or reflective-string resolution, and is not a complete generation/reachability analysis. Bootstrap adapters are inventoried separately. Concrete follow-up boundaries include Spring's CGLIB AbstractClassGenerator/Enhancer/KeyFactory generation and JDK proxy factories, Hibernate ClassLoaderServiceImpl.generateProxy and ByteBuddyState's DynamicType.Unloaded.load, and Byte Buddy class injectors/loaders plus Lookup/Unsafe/class-loader definitions. Spring MethodHandle lookup/invocation also remains unsupported. Pre-generate proxy/enhanced classes during the build and prove their method interception, state, constructors, identity and lazy-loading contracts before admitting those framework paths. No runtime class definition, general reflective invocation or framework startup is established by the plain-view subset.


The `method-types-v42` signature subset implements the MethodType factory/inspection descriptors in this report: Log4j ServiceLoaderUtil (zero/single/first-plus-array factories), Spring Data DefaultMethodInvokingMethodInterceptor (Class-array factory), and Spring Expression FunctionReference/ReflectionHelper (parameter count/array/type/last type). Exact-descriptor JVM/Wasm fixtures validate those operations, immutable transforms and method-type LDC. These callers still require MethodHandle lookup/invocation and additional reflection/JDK APIs; no complete caller/framework execution is implied. The next dynamic-runtime subset remains handle/proxy/enhancement behavior.


The `aot-handles-proxies-v43` milestone supplies fixed handle constants/invocation and caller/private/nest/special lookup, plus explicitly registered public-interface proxy shapes (`newProxyInstance`, `getProxyClass`, `isProxyClass`, `getInvocationHandler`). [The dynamic-runtime contract](aot-dynamic-runtime.md) maps the audited Spring/Hibernate/Byte Buddy sites to supported mechanisms, tested application AOT plans and explicit exclusions. Tests execute an unchanged pinned Byte Buddy-generated subclass, and compare application AOT advice/lazy-reference/scalar-dirty-state plans against real pinned Spring AOP and Hibernate proxy/enhancer JVM oracles. The framework-generated Hibernate classes remain on the build JVM; no complete Spring/Hibernate runtime class or startup is claimed in Wasm. Runtime CGLIB/Hibernate/Byte Buddy generation and class-definition entry points receive original-site diagnostics. All 226 bytecode tests pass; the pinned inventory changes only revision.


Revision `declared-methods-v44` begins reflection with original linked-class declared-method metadata. The member-reference inventory includes these APIs in Jackson, Classmate, H2 and framework utilities. JVM/Wasm tests cover declaration/flag/signature/exception discovery and unchanged pinned Spring Boot RabbitConnectionDetails$Address metadata; no full caller or framework startup is claimed. [The reflection contract](bytecode-reflection.md) records remaining inherited discovery, access-sensitive invocation, generic and annotation requirements. The reviewed pinned inventory changes only compiler revision; 231 bytecode tests pass.

Revision `reflection-metadata-v45` completes the selected linked-class reflection contract, including invocation, inherited lookup, generic/annotated signatures, parameters and runtime annotations. Tests execute selected pinned Spring ReflectionUtils invocation bodies (other declarations/initialization pruned) and unchanged Jakarta Persistence annotations. These results do not establish full-class Spring execution or framework startup. See [the detailed reflection contract](bytecode-reflection.md).

Validation: all 240 bytecode tests pass; the reviewed 63-JAR audit baseline passes with inventory counts unchanged and compiler revision `reflection-metadata-v45`.

Revision `core-text-v46` implements the first audited core text subset. Logback's unchanged pinned JsonEscapeUtil class now executes with the bundled StringBuilder, String.toCharArray and existing string character operations, including its static escape-table initializer. JVM/Wasm comparisons retain the actual library's behavior. See [the core JDK text contract](bytecode-core-jdk.md); this does not establish whole-Logback startup or complete core JDK coverage.

Validation: all 242 bytecode tests pass; the reviewed 63-JAR audit baseline passes with unchanged inventory counts and revision `core-text-v46`.

Revision `integral-values-v47` supplies integral parsing/formatting found in the member inventory, including Logback FormatInfo.valueOf, H2 and Spring/Hibernate conversion paths. Tests execute the unchanged pinned Logback FormatInfo class with the bundled wrappers and compare its actual parsing, value and failure semantics. This does not prove the other enclosing framework callers execute. See [the integral conversion contract](bytecode-core-jdk.md#integral-wrappers-and-radix-conversion).

Validation: all 244 bytecode tests pass; the reviewed 63-JAR audit baseline passes with unchanged inventory counts and revision `integral-values-v47`.

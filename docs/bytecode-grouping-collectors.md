# Sequential grouping collectors

Revision `grouping-collectors-v76` adds all three Java 17 Collectors.groupingBy overloads. Classification allocates downstream containers lazily per key, rejects null keys, combines buckets with the downstream combiner, and runs the downstream finisher once per bucket when required. The finisher function is obtained once at collector construction. Identity-finish downstream collectors retain IDENTITY_FINISH; other grouping collectors have no characteristics. The supplied map implementation is retained, including LinkedHashMap insertion order. Default grouping produces mutable maps/lists; immutable downstream collectors protect their buckets independently.

Tests compare default and supplied-map grouping, encounter order within buckets, direct combiner use, nested/mapped downstream collectors, nonidentity primitive-array accumulation, finisher-access timing, empty inputs, null classifier results, null downstreams, callback identity/failures and single-use streams with JVM execution, in both JAR orders and independent instances. Null classifiers are not eagerly rejected when no item is visited. No parallel/concurrent grouping or complexity guarantee is supplied.

The real-bytecode fixture verifies hashes for Spring Web MVC/Core 6.1.5 and Tomcat Embed Core 10.1.19. It extracts exactly the four consecutive collector-factory instructions from the original DefaultServerRequest.multipartData method: the Part::getName classifier, LinkedMultiValueMap constructor supplier, toList, and groupingBy. Those instructions and their original bootstrap handles execute unchanged in a static carrier. The complete original Spring MultiValueMap, MultiValueMapAdapter and LinkedMultiValueMap classes execute, with selected original Assert.notNull and CollectionUtils allocation helpers. Only Part.getName is retained from the original servlet interface; fixture objects supply names.

The fixture proves the original collector factory, actual multivalue-map implementation, bucket order, inherited map defaults, first-value extraction, mutation and null-name failures. It excludes servlet input/resource handling, DefaultServerRequest construction/caching, the rest of Part and complete HTTP/Spring execution. Instruction-sequence evidence is kept distinct from whole-method or closure-wide evidence.

This revision also tightens prior text subsets: Character code-point array helpers preserve explicit versus implicit bounds exception subtypes and null-check precedence; CharSequence counting and legacy byte String construction preserve null precedence for invalid bounds. Dedicated JVM comparisons cover these combinations. Ordinary BMP radix parsing keeps its small digit-block fast path so numeric-only workloads do not initialize the broader property table.

Primitive streams, spliterators, remaining stream/collector families, sorted/synchronized collections, charset/regex/locale text APIs, the core-JDK reachability gate and full I/O remain open.

Validation: the required offline bytecode suite passes all 338 tests with zero failures, errors or skips. The reviewed 63-JAR baseline changes only compilerRevision; dependency class/resource counts remain unchanged. Unicode case/property and traversal-oracle `--check` runs against JDK 17 pass.

# T22 Properties

Implemented: `java.util.Properties` (registered in `BytecodeExceptionRuntime`) as
`public class Properties extends Hashtable<Object,Object>` with the `protected Properties defaults` field, the
three constructors, `setProperty`, `getProperty(String)` / `getProperty(String,String)`, `propertyNames`,
`stringPropertyNames`, `putAll(Map<?,?>)`, `remove(Object,Object)`, `merge`, `forEach`, `toString`, `equals` and
the private helpers `enumerate`/`enumerateStringProperties`. `super.` is used exactly where the JDK reaches
into its own storage (`super.get` in `getProperty`, `super.put` in `putAll`, `super.keySet`/`super.get` in
`forEach`, `super.entrySet` in `toString`/`equals`, `super.remove`/`super.merge`), and virtual calls where the
JDK goes through the overridable members (`put` in `setProperty`, `getProperty` in the two-argument form,
`entrySet()` in the enumerate helpers, `defaults.getProperty`).

Left out: `load` (T23), `store`/`save` (write the current date, forbidden in the runtime), `list` (no print
streams), all XML methods, `rehash` (JDK no-op; declared absence is tested), the JDK's private `ConcurrentHashMap`
field, serialization hooks and the `Collections.synchronizedSet`-wrapped views.

Notes: the entries live in the inherited `Hashtable`, so multi-entry iteration order differs from the JDK; all
fixtures are order-independent except `propertyNames()`, which returns a fresh `Hashtable`'s `keys()` and
matches the JDK order for names in separate buckets (the runtime `Hashtable` uses the same
`(hash & 0x7FFFFFFF) % length` layout and high-to-low bucket enumeration). Names that share a bucket follow
this object's insertion order, which differs from the JDK. [Corrected in review.] The calibration pitfalls (inherited `equals`/`putAll`/`forEach`, the
`(this Map)` toString case, passing `n` to the `Hashtable` constructor) were avoided per the task. `kit check`
passed on the first run.

# T48 ConcurrentHashMap key sets, enumerations and remaining overrides

Implemented: in the existing `ConcurrentHashMap` — `newKeySet()` / `newKeySet(int)` (fresh plain map with
`Boolean.TRUE` values), `keySet(V)` (a new view per call, `NullPointerException` for null), `KeySetView`
`getMappedValue()` and `forEach(Consumer)`, `keys()` / `elements()` (the T47 key and value iterators now also
implement `Enumeration` with `hasMoreElements()` / `nextElement()`), `mappingCount()`, `contains(Object)`,
`getOrDefault` through the virtual `get`, `forEach(BiConsumer)` and `replaceAll(BiFunction)` through a new
non-preloading `LiveWalker` (the next node is found only after the current node's callback returned), and the
`ValuesView` / `EntrySetView` `forEach` / `removeIf` (removeIf removes through `replaceNode(k, null, v)`; the
entry predicate receives an `AbstractMap.SimpleImmutableEntry`).

Left out: the parallel bulk operations (`forEach(long, ...)`, `search*`, `reduce*`, `forEachKey/Value/Entry`,
`searchKeys/Values/Entries`, `reduceKeys/Values/Entries*`), a `KeySetView.removeIf` override (the `Collection`
default — iterator plus `remove` — is exactly the JDK's behaviour) and everything T47 left out.

Notes: `kit check T48` and the T47 regression both passed on the first check. The `Spy` fixture confirms the
JDK self-call shape: only `getOrDefault -> get` and `contains -> containsValue` reach overridable methods;
`forEach`, `replaceAll`, `keySet(V).add/addAll`, the views' `removeIf` and `toArray` call none of
`entrySet()`, `get()`, `put()`, `putIfAbsent()` or `size()`. The live walk matters for `defaultsAndForEach`:
the T47 preloading iterator would have reported key 2 (preloaded before the callback removed it) while the
JVM walks slots live and skips it.

# T50 ReadWriteLock and ReentrantReadWriteLock
Implemented: `java.util.concurrent.locks.ReadWriteLock` (readLock, writeLock) and
`ReentrantReadWriteLock` (both constructors, covariant readLock/writeLock, final isFair, getReadLockCount,
getReadHoldCount, isWriteLocked, isWriteLockedByCurrentThread, getWriteHoldCount, toString) with the
`public static` nested `ReadLock` and `WriteLock` (protected constructor, lock, lockInterruptibly, tryLock,
unlock, toString; WriteLock also isHeldByCurrentThread and getHoldCount). Single-threaded contract: two plain
counters `readHolds`/`writeHolds` in the outer class, read always succeeds (downgrade), write `tryLock()`
returns false only on a held-read/none-written upgrade, 65535-limit `Error("Maximum lock count exceeded")`
checked before incrementing, and the two distinct `IllegalMonitorStateException` unlock failures.
Left out: all queue/waiter inspection methods, `newCondition()`, timed `tryLock`, `Sync`/`HoldCounter`
machinery, `serialVersionUID`/`readObject` (they need `Thread`, `Condition`, `TimeUnit` or AQS, none in the
runtime); `equals`/`hashCode` not overridden (identity).
Notes: nested locks read `lock.readHolds`/`lock.writeHolds` directly; no method in the outer class or nested
locks calls another overridable method of the lock hierarchy (verified by the `noSelfUse`/`protectedConstructors`
logging fixtures). `WriteLock.lock()`/`lockInterruptibly()` throw
`IllegalMonitorStateException("write lock would block forever: read lock held")` for the read-to-write upgrade
the JDK would deadlock on forever. Protected constructors dereference the argument with
`Objects.requireNonNull`, so `new ...ReadLock(null){}` throws `NullPointerException`. Check passed on the
first attempt.

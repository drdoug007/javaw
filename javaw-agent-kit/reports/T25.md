# T25 FilterInputStream, DataInput and DataInputStream

Implemented: `java/io/FilterInputStream.java` (protected `in` field, one-line delegations, `read(byte[])`
through the overridable 3-argument read), `java/io/DataInput.java` (plain 14-method interface, no
`readLine`), `java/io/DataInputStream.java` (8-byte `readBuffer`, `bytearr`/`chararr` readUTF buffers,
`readFully` loop with `checkFromIndexSize` and `EOFException`, `skipBytes` via `in.skip` with the `int`
cast, big-endian primitives with `& 0xff` masking and the masked low half in `readLong`,
`Float.intBitsToFloat`/`Double.longBitsToDouble`, static `readUTF(DataInput)` with the JDK's
ASCII-run-then-multibyte two-loop decode, buffer growth only when `bytearr.length < utflen`, and the
JDK malformed-input messages). Registered all three with `kit register`.

Left out: `DataInputStream.readLine()` and `DataInput.readLine()` (deprecated; the JDK version wraps `in`
in a `java.io.PushbackInputStream`, which the runtime does not have) — `leavesOutReadLine` checks that a
call to `DataInputStream.readLine()` is rejected before WAT generation. `FilterInputStream` leaves
`readAllBytes`/`readNBytes`/`skipNBytes`/`transferTo` inherited from `InputStream`.

Notes: the JDK 21 `readUTF` decode is a two-loop structure — a first `while` consumes the leading run of
bytes `<= 127` (breaking, not continuing, at the first multibyte lead), and a second `while` decodes the
rest on `c >> 4`. The first loop is only a fast path: a single loop over `c >> 4` gives the same results,
including "around byte 3" for `41 e0 80 ff` [corrected in review]; implemented with `if`/`else` on `c >> 4` per the rules (no int switch needed, no pattern
variable in the `instanceof`). `kit check` passed on the first run.

# T14 MessageDigest SHA-1, MD5 and SHA-512

Implemented: `javaw.runtime.Sha1` (FIPS 180 SHA-1, 80 rounds with the rotate-by-1 message schedule),
`javaw.runtime.Md5` (RFC 1321, little-endian words, output and bit length), and `javaw.runtime.Sha512` (SHA-512
and SHA-384 on `long` words, 128-byte blocks, 16-byte length field, with the `sha512`/`sha384` factories).
`Digests.create` matches the JDK aliases for each one. The constant tables were copied from the JDK's
`sun.security.provider` `MD5`, `SHA` and `SHA5`; the round logic was written separately.

Left out: SHA-224, SHA-512/224, SHA-512/256, SHA3-*, MD2, and the MD5 OID aliases (JDK 21 has them, JDK 17
does not).

Notes: the local session timed out after 240 minutes with SHA-512 and SHA-384 still failing. The engines were
right. The bug was in T13's `BlockDigest.engineDigest`, which wrote the length field with `bits >>> (8 * i)`
for all 16 bytes. Java masks a long shift to 6 bits, so the high 8 bytes repeated the bit count instead of
staying zero. A reviewer fixed it by writing only the low 8 bytes. The hint for step 0 described the rule but
not this trap.

# T57 java.sql exception family

Implemented: `java.sql.SQLException` (eight constructors, `getSQLState`/`getErrorCode`/`getNextException`/
`setNextException`, `Iterable<Throwable>` iterator over the exception and its cause chain with the JDK's
snapshot-at-creation semantics), `SQLWarning` (eight constructors, `getNextWarning` converting
`ClassCastException` to `Error`, `setNextWarning`) and the eleven subclasses: `SQLNonTransientException`,
`SQLTransientException`, and the six/leaves under each — `SQLDataException`,
`SQLFeatureNotSupportedException`, `SQLIntegrityConstraintViolationException`,
`SQLInvalidAuthorizationSpecException`, `SQLNonTransientConnectionException`, `SQLSyntaxErrorException`
(under non-transient) and `SQLTimeoutException`, `SQLTransactionRollbackException`,
`SQLTransientConnectionException` (under transient), each with the eight delegating constructors.

Left out: `BatchUpdateException` (long[] update counts + serialization helpers), `SQLClientInfoException`
(Map + ClientInfoStatus enum) and `SQLRecoverableException` (no pinned library uses it) — all checked to
stay unlinked; `DriverManager` and its log-writer side of the JDK constructors (JDK default log writer is
null, so nothing observable is lost); `serialVersionUID` fields and CAS/lock machinery
(`AtomicReferenceFieldUpdater`, `volatile`) — `setNextException` is a plain walk-and-append loop.

Notes: first `kit check` passed. The iterator's field initializers must call `getNextException()`/`getCause()`
once each, virtually, on `this` (the `Spy` fixture verifies the exact log of overridable calls), and
`setNextException` must walk the `next` fields rather than `getNextException()` so it stays unlogged and
unaffected by overrides. `java.sql` compiles fine into the `java.base` patch module.

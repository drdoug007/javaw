# T33 BufferedInputStream and BufferedOutputStream

Implemented: `java.io.BufferedInputStream` (constructors, `read()`, `read(byte[],int,int)` via `read1`, `skip`,
`available`, `mark`, `reset`, `markSupported`, `close`, `transferTo`, plus the private
`getInIfOpen`/`getBufIfOpen`/`ensureOpen`/`fill` helpers) and `java.io.BufferedOutputStream` (constructors,
`write(int)`, `write(byte[],int,int)`, `flush`, plus the private `flushBuffer`/`growIfNeeded` helpers), both
registered with `kit register`.

Left out: the JDK's `synchronized` wrappers/`implXxx` split, `InternalLock`/`Unsafe`, the lazy input buffer and
the 512-byte virtual-thread output buffer (buffers are allocated eagerly at full size, as JDK 21 does for
subclasses and platform threads); no `write(byte[])`/`close()` overrides on `BufferedOutputStream` and no
`read(byte[])` override on `BufferedInputStream` — the inherited `Filter*Stream` versions are the JDK behaviour.

Notes: first `kit check` passed without a fix. Tricky details matched from the task spec: `fill()` sets
`count = pos` before the source read and compares `markpos == -1` (only `reset()` uses `< 0`);
`read(byte[],int,int)` uses the message-less `IndexOutOfBoundsException` bounds test (not
`InputStream.checkFromIndexSize`) and asks the source's `in.available()` between chunks; `transferTo` branches on
`getClass() == BufferedInputStream.class`; the output direct-write path compares `len >= maxBufSize` and the
buffered path lets `System.arraycopy` report bad ranges after a possible flush.

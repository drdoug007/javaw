# T76 CompletableFuture single-threaded core

Implemented: `java.util.concurrent.CompletionException` (protected no-arg/String + public (String, Throwable)/
(Throwable), where `(Throwable cause)` delegates to `super(cause)`), the `CompletionStage` interface (the eight
abstract members: thenApply, thenAccept, thenRun, thenCompose, handle, whenComplete, exceptionally,
toCompletableFuture), and `CompletableFuture` (nil/AltResult result encoding, `complete`/
`completeExceptionally`/`cancel`/`completedFuture`/`failedFuture`, `isDone`/`isCancelled`/
`isCompletedExceptionally`, `get`/timed `get`/`join`/`getNow` with the `reportGet`/`reportJoin` exception
rules, all seven stage methods plus `toCompletableFuture`, the nested `Completion` class with an `int kind`
(APPLY/ACCEPT/RUN/COMPOSE/HANDLE/WHEN/EXCEPTIONALLY/RELAY) and one shared `run` for the now-path and
`fire()`, and the JDK `postComplete` loop copied from the task). All three registered with `kit register`;
`docs/bytecode-completable-future.md` created.

Left out: everything needing an executor or another thread (`runAsync`, `supplyAsync`, `completeAsync`, every
`...Async` stage, `defaultExecutor`, and anything mentioning `Executor`/`ForkJoinPool`/`Thread`), time
(`orTimeout`, `completeOnTimeout`), and the unreferenced members listed in the task (`thenCombine`/either/both
family, `allOf`/`anyOf`, `exceptionallyCompose`, `obtrude*`, `getNumberOfDependents`, the stage factories,
`resultNow`/`exceptionNow`/`state`, `toString`). T75's `Future`, `ExecutionException`, `CancellationException`
and `TimeoutException` are used unchanged.

Notes: the first check failed only on a javac error in the runtime build (`reportGet` throws the checked
`ExecutionException` without declaring it); fixed with a `throws` clause and the second check passed.
Behavioural details that mattered: `run` skips a dependent that was already completed by hand *including*
not invoking its function (the `pendingExceptional` fixture logs prove it), `thenCompose` calls
`toCompletableFuture()` on the returned stage inside the `try` so a `null` stage becomes
`CompletionException<NullPointerException>`, and a pending inner stage gets a RELAY `Completion` pushed on it
so the outer dependent completes when the inner one does.

# T52 TimeUnit conversions

Implemented: `java.util.concurrent.TimeUnit` enum in the bundled exception runtime, registered via
`kit register`. The seven constants in JDK order (`NANOSECONDS` … `DAYS`) with no constant-specific class
bodies; the seven `*_SCALE` `private static final long` constant expressions; the `scale`/`max*` and
`microRatio` (`long`)/`milliRatio`/`secRatio` (`int`) instance fields; the `private TimeUnit(long)`
constructor; `private static long cvt(long, long, long)`; `convert(long, TimeUnit)` (switch on `this`
with a `default`, exactly like the JDK, so no synthetic switch class is generated); and
`toNanos`/`toMicros`/`toMillis`/`toSeconds`/`toMinutes`/`toHours`/`toDays`, all copying the JDK 17/21
implementation with truncating division and `Long.MAX_VALUE`/`Long.MIN_VALUE` saturation. `values()`,
`valueOf`, `name()`, `ordinal()`, `toString()`, `compareTo`, `equals` and `hashCode` come from javac and
the runtime `java.lang.Enum`.

Left out: `sleep(long)`, `timedWait(Object, long)`, `timedJoin(Thread, long)` and the private `excessNanos`
(need threads, monitors and a clock); `convert(java.time.Duration)`, `toChronoUnit()` and `of(ChronoUnit)`
(`java.time` is not in the runtime). All six are verified to stay unlinked by
`leavesOutSleepingAndJavaTime`.

Notes: nothing surprising — the implementation is a copy of the JDK semantics, and the differential
test passed on the first `kit check`. The `HOURS`/`DAYS` micro-ratio wraparound pitfall was avoided by
declaring `microRatio` as `long` from the start.

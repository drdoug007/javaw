# T32 BufferedReader

Implemented: `java.io.BufferedReader` (one new file in the exception runtime) with the JDK 21 structure: the
fields `in`, `cb`, `nChars`, `nextChar`, `markedChar` (`UNMARKED`/`INVALIDATED`), `readAheadLimit`, `skipLF`,
`markedSkipLF`; constructors `(Reader)` and `(Reader,int)`; `ensureOpen`, `fill`, `read()`, `read1`,
`read(char[],int,int)`, `readLine`, `skip`, `ready`, `markSupported`, `mark`, `reset`, `close`. The JDK
call pattern is kept exactly: `fill` reads the whole free buffer and retries on 0, `read(char[],int,int)`
topps up via `in.ready()` and `read1` takes the direct path only with an empty buffer, no valid mark and no
pending `\n`, `readLine` folds the package-private `readLine(false, null)` body in (only `\n`/`\r`/`\r\n` end
a line, `\r` defers swallowing the `\n`), and `mark`/`reset` validate the read-ahead limit with buffer
shuffling/growth and invalidation inside `fill`. Registered with `kit register`.

Left out: `lines()` (needs `java.io.UncheckedIOException`, not in the runtime, unused by the pinned set —
the test checks it stays unlinked), `read(CharBuffer)` and `Readable` (no `java.nio` in the runtime), and the
JDK's package-private `readLine(boolean, boolean[])` (its `readLine(false, null)` body is inlined).

Notes: first `kit check` passed (1 attempt). The subtle case is `read1` being called with `(off + n, len - n)`
in the top-up loop: with buffer 4 over `line1\nline2\r\nrest of the text` the inherited `read(char[])` on a
3-char array stops after 3 chars (`i`, `ne`) because the second `read1` asks for only `len - n = 2`, which
keeps `2` chars buffered so `transferTo` reads them in 8192-char chunks — the `Spy` log
`R3:0,3 Y R8192:0,8192 R8192:0,8192 M2` matches the JVM.

# T24 FilterOutputStream, DataOutput and DataOutputStream

Implemented: `java/io/FilterOutputStream.java` (protected `out`, private `closed`, delegating
`write(int)`/`write(byte[])`/`write(byte[],int,int)` with the JDK per-byte loop and
`Objects.checkFromIndexSize` range message, `flush()`, and `close()` with the JDK
flush-then-close suppression rules), `java/io/DataOutput.java` (the 14 abstract methods, no defaults),
`java/io/DataOutputStream.java` (protected `written` with `incCount`'s `Integer.MAX_VALUE` clamp, the
reusable 8-byte `writeBuffer` for big-endian short/char/int/long/float/double, direct-sink
`write(int)`/`write(byte[],int,int)`/`flush()`/string writes, modified-UTF-8 `writeUTF` with the
reusable `bytearr`, the too-long check and `tooLongMsg`, `size()`), and
`java/io/UTFDataFormatException.java`. All four registered; `docs/bytecode-data-output-stream.md` added.

Left out: nothing else exists on these JDK 21 classes except the package-private
`static int writeUTF(String, DataOutput)` shared with `ObjectOutputStream`; the encoding is written
inside `writeUTF(String)` instead. No `synchronized`/`volatile`/`closeLock` per RULES.md.

Notes: first check failed on the `writeUTF` fixtures for two reasons, both fixed in one pass: the
encoding loop started at index 0 and overwrote the big-endian length prefix stored at `bytearr[0..1]`
(stream came out with the prefix missing and the characters shifted left), and the branch conditions
used `c > 0x007F && c <= 0x07FF` for the 2-byte case, which sent `\0` as 3 bytes (`e0 80 80`) instead of
the JDK's 2 bytes (`c0 80`); the JDK tests `c > 0x07FF` for the 3-byte case in both the length
computation and the encoding. Second check: PASS.

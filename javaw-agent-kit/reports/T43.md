# T43 LongAdder and LongAccumulator

Implemented: `java.util.concurrent.atomic.LongAdder` (constructor, `add`, `increment`, `decrement`, `sum`,
`reset`, `sumThenReset`, `toString`, `longValue`, `intValue`, `floatValue`, `doubleValue`) and
`java.util.concurrent.atomic.LongAccumulator` (constructor, `accumulate`, `get`, `reset`, `getThenReset`,
`toString`, `longValue`, `intValue`, `floatValue`, `doubleValue`), both `extends Number implements
java.io.Serializable` with one plain `long` field and no `final` members, registered by `kit register`.

Left out: serialization (`writeReplace`, `readObject`, `SerializationProxy` — the test checks
`writeReplace` stays unlinked), `byteValue`/`shortValue` (the runtime `Number` versions are exactly the JDK's),
`equals`/`hashCode` (identity, as in the JDK), and the `Striped64`/`Cell` machinery with `Unsafe`/`VarHandle`
internals (replaced by the single plain field per the single-threaded contract).

Notes: kit check passed on the first run, matching the task's calibration. `accumulate` assigns `base` only
after `function.applyAsLong(base, x)` returns, so null/throwing functions leave `base` unchanged;
`sumThenReset`/`getThenReset` read `base` directly and log nothing, while every `Number` conversion routes
through the virtual `sum()`/`get()` once, which the `LoggingAdder`/`LoggingAccumulator` call-pattern fixtures
confirm.

# T10 BitSet
Implemented: `java/util/BitSet.java` in the bundled exception runtime — `BitSet()`, `BitSet(int)`, `get`, `set` (single, boolean, range), `clear` (single, range, all), `flip`, `nextSetBit`, `nextClearBit`, `previousSetBit`, `previousClearBit`, `length`, `size`, `isEmpty`, `cardinality`, `toString`; storage `long[] words` + `int wordsInUse` with `wordIndex`/`ensureWords`/`recalculateWordsInUse`/`checkRange` helpers; implements `Cloneable`, `java.io.Serializable`. Registered via `kit register` (appended to the `java/util` `List.of(...)` in `BytecodeExceptionRuntime.java`).
Left out: `get(int,int)` and `stream()` (checked rejected by `rejectsUnlinkedMembers`) and everything T11 adds (`or`, `and`, `xor`, `andNot`, `intersects`, `equals`, `hashCode`, `clone`, `toByteArray`, `toLongArray`, `valueOf`, `flip(int,int)`, `set(int,int,boolean)`) — no `clone` body despite `Cloneable`, per the task.
Notes: `flip(int)` written as a direct XOR store (`words[w] ^= 1L << bitIndex` then `recalculateWordsInUse`) failed twice with the bits silently never setting: it grew the array without raising `wordsInUse`, and `recalculateWordsInUse` only shrinks it, so flipped-on bits stayed invisible to `get`/`length`. This was a logic bug in the attempt (the same code fails on the JVM), not a Wasm or compiler problem. Rewrote `flip` as `get(i) ? clear(i) : set(i)`, which is observably identical to the JDK (a set bit implies its word is present, so the JDK's unconditional grow is a no-op there) and routes through `set`, which raises `wordsInUse`. Third check passed.
